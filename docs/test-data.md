# Test data and parity fixtures

The Rust tests compare the port with fixtures that the pinned R package (DataQualityDashboard 2.9.0) produced. This page
says what those fixtures are built from, where the source data comes from, what its licence allows, and how to rebuild
everything. The Rust tests themselves need no R, no Java and no download: they read the committed fixtures.

## What is in `tests/oracle/generated`

| Folder | Built from | Data | Generator (in `tests/oracle/`) |
|---|---|---|---|
| `catalog`, `enumeration`, `render.json`, `evaluation.json`, `summary.json`, `exports`, `manifest.json` | The pinned R package only | none | `generate.R` |
| `database/*`, `duckdb/*` (except `duckdb/gibleed`), `postgres/*` | Tiny scenario databases the generators create | Hand-made, synthetic | `generate.R` (database), `duckdb-cases.R`, `postgres-cases.R` |
| `gibleed/sqlite`, `duckdb/gibleed`, `upstream` | Eunomia **GiBleed**, CDM 5.3 | Synthetic (Synthea), 2,694 people | `gibleed-cases.R`, `duckdb-cases.R`, `upstream-testthat-cases.R` |
| `eunomia/synthea27nj` | Eunomia **Synthea27Nj**, CDM 5.4 | Synthetic (Synthea), 28 people | `eunomia-cases.R` |
| `eunomia/mimic` | Eunomia **MIMIC**, CDM 5.3 | **De-identified real patient data**: the MIMIC-IV demo, 100 people | `eunomia-cases.R` |

The committed databases are `eunomia/mimic/cdm.sqlite` (42 MB), `gibleed/sqlite/gibleed-copy.sqlite` (20 MB),
`eunomia/synthea27nj/cdm.sqlite` (13 MB) and `duckdb/gibleed/cdm.duckdb` (10 MB), plus a few dozen files of 100 KB or less.

## Licences and what is safe to publish

- **GiBleed and Synthea27Nj** are generated by [Synthea](https://synthetichealth.github.io/synthea/) and converted to OMOP
  by OHDSI's ETL-Synthea (the `cdm_source` table in each file says so). They contain no real patients. I did not
  check the terms of the OHDSI `EunomiaDatasets` repository that distributes them.
- **MIMIC** is not synthetic. Its `cdm_source` table reads "MIMIC IV", holder PhysioNet, ETL `OHDSI/MIMIC`, with 100
  people, 852 visits and 338,550 measurements. That is the 100-patient demo of MIMIC-IV, de-identified data from real
  patients at Beth Israel Deaconess Medical Center.
  - The raw [MIMIC-IV Clinical Database Demo](https://physionet.org/content/mimic-iv-demo/) is open access under the
    Open Data Commons Open Database License (ODbL) v1.0, and PhysioNet asks for a citation as shown on its page. The full
    MIMIC-IV needs credentialed access and must never be committed.
  - The OMOP conversion, [MIMIC-IV demo data in the OMOP Common Data Model](https://physionet.org/content/mimic-iv-demo-omop/)
    (v0.9), is also open access under ODbL; PhysioNet's project metadata lists the licence as ODbL. Eunomia
    redistributes a copy of it through OHDSI's `EunomiaDatasets`. I did not compare that copy with PhysioNet's file or read
    `EunomiaDatasets`' own terms, so the notice in `THIRD_PARTY_NOTICES.md` names PhysioNet as the source.
  - ODbL attaches conditions to redistributing the database or a derived one: attribution, a licence notice, and
    share-alike for derived databases. My reading, not legal advice. The conditions apply to the data, not to this
    repository's Apache-2.0 code.

**Decision: the MIMIC database stays in the repository**, because the demo is open access and can be shared on those
terms. To meet them, [`THIRD_PARTY_NOTICES.md`](../THIRD_PARTY_NOTICES.md) names the source, the licence and the citation
requirement, and says that the database file is under ODbL while the code is Apache-2.0. Two things keep that honest:

- Keep the file as Eunomia 2.1.0 delivers it (not yet compared byte for byte: see open item 5 in `THIRD_PARTY_NOTICES.md`). A modified copy would be a derived database that must stay under ODbL and
  be marked as changed.
- Never commit the full MIMIC-IV, or any MIMIC table beyond the demo. Those need PhysioNet credentialed access and a
  data use agreement.

## Getting the datasets

All three are distributed through the R package [Eunomia](https://cran.r-project.org/package=Eunomia), which downloads
them from <https://github.com/OHDSI/EunomiaDatasets> on first use. The fixtures were generated with **Eunomia 2.1.0**
(recorded in `eunomia/*/timing.json`). Later releases change defaults (2.2.0 moves the default GiBleed to CDM 5.5), so
always pass the CDM version explicitly.

```r
install.packages("remotes")
remotes::install_version("Eunomia", "2.1.0")

dir <- Sys.getenv("DQD_EUNOMIA_DIR")            # where the SQLite files should end up
dir.create(dir, recursive = TRUE, showWarnings = FALSE)
Sys.setenv(EUNOMIA_DATA_FOLDER = file.path(dir, "downloads"))   # cache for the downloaded archives

want <- list(c("GiBleed", "5.3"), c("MIMIC", "5.3"), c("Synthea27Nj", "5.4"))
for (w in want) {
  f <- Eunomia::getDatabaseFile(w[1], cdmVersion = w[2], dbms = "sqlite", overwrite = TRUE)
  file.copy(f, file.path(dir, sprintf("%s_%s.sqlite", w[1], w[2])), overwrite = TRUE)
}
```

This gives `GiBleed_5.3.sqlite`, `MIMIC_5.3.sqlite` and `Synthea27Nj_5.4.sqlite`, the names the scripts expect. I could not
run this snippet here (no Eunomia in the sandbox), so check it against `?Eunomia::getDatabaseFile`. For DuckDB, call
`getDatabaseFile("GiBleed", cdmVersion = "5.3", dbms = "duckdb")` for the GiBleed file and copy it to `GiBleed_5.3.duckdb` in `DQD_EUNOMIA_DIR`. MIMIC does not load into DuckDB
that way (its ids reach about 7.5e18); `docs/performance.md` explains how that file was built.

A rebuilt SQLite file will not be byte-identical to the committed one, so check the content instead:

| Dataset | `person` | `visit_occurrence` | `condition_occurrence` | `measurement` | `drug_exposure` |
|---|---|---|---|---|---|
| GiBleed (5.3) | 2,694 | 1,037 | 65,332 | 44,053 | 67,707 |
| MIMIC (5.3) | 100 | 852 | 16,441 | 338,550 | 18,229 |
| Synthea27Nj (5.4) | 28 | 1,791 | 470 | 10,040 | 883 |

## Rebuilding the fixtures

Prerequisites (R 4.5.2, the pinned DataQualityDashboard, Java for `rJava`, PowerShell 7) are listed in
[`CONTRIBUTING.md`](../CONTRIBUTING.md#regenerating-the-parity-fixtures), with the `DQD_*` environment variables the scripts
read. PowerShell 7 also runs on Linux and macOS. The R packages used for the committed fixtures: DataQualityDashboard
2.9.0, DatabaseConnector 8.0.0, Eunomia 2.1.0, and for DuckDB the R `duckdb` package 2.0.0 (engine 2.0.0).

One step at a time, in this order (the scripts run them one after another because parallel runs on these datasets have
exhausted disks before; allow about 25 minutes and several GB of temporary space):

```sh
pwsh -NoProfile -File scripts/regenerate-oracles.ps1 -Only core        # catalog, rendering, evaluation, exports, scenarios
pwsh -NoProfile -File scripts/regenerate-oracles.ps1 -Only gibleed     # needs GiBleed_5.3.sqlite in DQD_EUNOMIA_DIR
pwsh -NoProfile -File scripts/regenerate-oracles.ps1 -Only upstream    # replays upstream's testthat scenarios on a GiBleed copy
pwsh -NoProfile -File scripts/regenerate-oracles.ps1 -Only eunomia     # needs MIMIC_5.3.sqlite and Synthea27Nj_5.4.sqlite
```

Then check the diff and run the tests:

```sh
git diff --stat tests/oracle/generated
cargo test --workspace --release
```

Not covered by `regenerate-oracles.ps1`:

- **DuckDB fixtures.** The script has no `duckdb` step. Run the generator by hand with a GiBleed DuckDB file built as
  above:
  `Rscript --vanilla tests/oracle/duckdb-cases.R "$DQD_UPSTREAM" tests/oracle/generated "$DQD_EUNOMIA_DIR/GiBleed_5.3.duckdb"`
  (set `DQD_R_LIBRARY` first). It writes `tests/oracle/generated/duckdb`.
- **PostgreSQL fixtures.** The `postgres` step starts a private PostgreSQL 18 cluster on port 54329
  (`scripts/postgres-oracle.ps1`). `tests/oracle/postgres-cases.R` still hard-codes the JDBC driver directory, a work
  directory and the GiBleed source database (lines 145 to 147); edit those to your machine first. Download the driver
  with `scripts/download-jdbc.R`.
- **Machine paths.** The R generators fall back to a maintainer's Windows library path when `DQD_R_LIBRARY` is unset, so
  always set it. Existing fixtures also record such paths in `options.json`, logs and results; regenerating from your
  own machine replaces them with yours, which is why the diff needs reviewing.

I could not run any of the R steps in the sandbox (R 4.3.3 without the packages, no Java or PowerShell), so these
commands come from reading the scripts, not from a run.
